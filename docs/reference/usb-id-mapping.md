# The USB block id (`usb_id`) ↔ `@model`

Over USB, POD Go refers to a block by a **small integer** (`usb_id`), not by its `@model`
string. This page covers the wire **encoding** and the **complete `usb_id → @model` mapping** —
which is derivable directly from POD Go Edit, no captures required.

↩ [reference index](README.md)

## The mapping: `usb_id` = index into `PodGo.sym`

**`usb_id` is the 0-based index of a model's `symbolicID` in POD Go Edit's
`Resources/PodGo.sym`** (627 JSON entries, each `{symbol, parameters}` — the array *position*
is the id). So `PodGo.sym[289] = HD2_AmpDelSol300` ⇒ Del Sol 300 is usb_id `289`.

How the app uses it (from decompiling `POD Go Edit`, x86-64, unstripped):

- `HelixSymbolTable::initFromTableData` loads `PodGo.sym` into an
  `L6HashTable<L6String, ModelEntry*>`; each `ModelEntry`'s first field is its id (= its index).
- `HelixSymbolTable::lookupModel(symbolicID)` → `usb_id`; `lookupModel(unsigned int)` → the
  reverse. These are called throughout `L6PodGoPreset`'s Read/WriteHelixCore\* code — the
  editor holds the map internally, which is why it can send the right id with no device round-trip.

The complete 627-pair table lives in
[`registry/usb-id-map.json`](../../registry/usb-id-map.json), regenerated by
[`tools/gen_usb_id_map.py`](../../tools/gen_usb_id_map.py) (reads `PodGo.sym`, self-checks
against the known hardware pairs, aborts if any mismatch). Of the 627 symbols, **573 are the
user-selectable catalog** (`PodGoModelDefs.bin`); the other 54 are internal (`FXLoopMono1–4`,
`ImpulseResponse*`, `LooperStereo`, …).

`PodGo.sym` order is the Helix/HX platform's **global, historically-assigned** model index
(early models grouped by category — amps `0–44`, cabs `45–74`, delays `75–86`, … — then newer
models appended across firmware updates). That's why `usb_id` is **not** the
`PodGoModelDefs.bin` array index (which is in catalog order) and why no flat catalog re-ordering
reproduces it — but within any one category the ids stay in catalog order (monotonic).

## Encoding — how a `usb_id` is stored on the wire

In each occupied slot of the preset stream the `usb_id` is a **MessagePack uint** in the map
field keyed `0x19`, written as `c2 19 <uint> 1a ff 09` (the `c2` and `19` are the field's
`false` flag and the `0x19` key; the value is a single msgpack integer):

- fixint (`< 0x80`, 1 byte, e.g. `c2 19 5c` = 92), `0xcc` = uint8 (`c2 19 cc e0` = 224),
  `0xcd` = uint16 **big-endian** (`c2 19 cd 011e` = 286). The width scales with the value —
  proof it's one integer, not a packed pair.
- The **Looper** is the exception: `84 08 <uint> 09` (a plain `c2 19` scan misses it), but the
  id is still the `PodGo.sym` index (`127` = `HD2_LooperMono`, `430` = `HD2_LooperOneSwitchMono`).

Decoded by [`tools/podgo_usb.py`](../../tools/podgo_usb.py). The editor **sends** these ids too
(host→device set-model / add-block), so the encoding is used both directions. This wire-decode
rule is the project's first ✅ verified rule ([`usb-id-decode`](../../registry/rules.json)); see
[knowledge/verified.md](../knowledge/verified.md).

## Hardware confirmation

- **Retrospective:** `PodGo.sym[usb] == symbolicID` for every pair read off real captures —
  the 10 calibration pairs, the loopers, and every set-model observed (21+ total), 100%.
- **Blind predictive (firmware v2.50):** predicted `PodGo.sym[41] = HD2_AmpUSDoubleNrm` ⇒
  setting the amp to **"US Double Nrm"** should send `c2 19 29` (0x29 = 41). On the unit it did,
  exactly. A live-preview scroll also swept consecutive amps `39–42` (US Deluxe/Double Nrm+Vib),
  matching the list order. Matching that many exact positions out of 627 by chance is ~0.

## Lesson: why this was hard to find

The map is a *local* file, but it hid in plain sight. `PodGo.sym` looks like a `symbol →
parameters` list, so it was dismissed early — the non-obvious part is that **the entry's
position is the id** (no explicit id field). A long detour (searching the binary for a
`usb_id` array in every model order/width, for FNV-hashed keys, for a device-sent manifest;
confirming the pickers fetch nothing over USB) all came up empty precisely because the answer
was an *implicit* index in a file that carries no id column. When a value isn't stored, check
whether an **ordering** encodes it. (The superseded capture-alignment tool
`tools/decode_model_list.py` was built before this was found; it's no longer needed.)
