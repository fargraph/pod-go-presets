# Code Conventions

How the code in this repo is written — the `tools/` Python scripts and the
`registry/` JSON files. Follow these so new code reads like the existing code.

↩ [conventions index](README.md)

## Python (`tools/`)

- **Standard library only.** The scripts import `json`, `re`, `glob`, `os`,
  `sys` — nothing external. Keep it that way; a contributor should be able to run
  every tool with a bare Python 3 install and no `pip install`.
- **`podgo.py` is the shared library.** Load/parse, chain inspection,
  classification, taxonomy, and canonical naming all live in
  [`tools/podgo.py`](../../tools/podgo.py). Other scripts add it to the path and
  import it rather than re-implementing:

  ```python
  import sys, os
  sys.path.insert(0, os.path.dirname(os.path.abspath(__file__)))
  import podgo
  ```

- **`REPO` is derived from `__file__`**, never hard-coded, so tools run from any
  working directory: `REPO = os.path.dirname(os.path.dirname(os.path.abspath(__file__)))`.
- **Read-only vs. generators are separate.** `podgo.py` mutates nothing. Scripts
  that *write* (`harvest_blocks.py`, `coverage.py`, `gen_matrix.py`) say so and
  own a clearly named output. `validate_presets.py` only reads and reports.
- **Every script has a module docstring** that states what it does and ends with
  a `Usage:` line, plus a `main()` guarded by `if __name__ == "__main__":`.
- **Validators exit non-zero on failure.** `validate_presets.py` distinguishes
  `ERROR` (fails the run, exit 1) from `WARN` (reported, doesn't fail).
- **Comments explain *why*, not *what*** — e.g. the trailing-comma recovery in
  `load_pgp` is commented because tolerating invalid JSON is surprising.
- **Text I/O is UTF-8-explicit** (`open(path, encoding="utf-8")`), and parsing is
  tolerant where Pod Go is (recover from a trailing comma, then flag it).
- **Style:** `snake_case`, small pure functions, minimal state; match the
  surrounding code's density and idiom.

## JSON (`registry/`)

- **Every registry file is self-describing:** a top-level `"schema"` tag with a
  version (`"podgo-blocks/v1"`, `"podgo-combinations/v1"`,
  `"podgo-reference-models/v1"`) and a `"note"` explaining the file and pointing
  at its authoritative doc.
- **Generated files announce it** in their `note` and name the tool that writes
  them. Don't hand-edit a generated file — re-run its generator. (See the tool
  map in [naming-and-registry.md](../presets/naming-and-registry.md).)
- **Device field names keep their `@` prefix** exactly as Pod Go emits them
  (`@model`, `@type`, `@position`, `@enabled`) — see
  [pgp-format.md](../presets/pgp-format.md).
- **Status is authoritative in `combinations.json`**, mirrored elsewhere (the
  `_broken` filename suffix, `presets.csv`) — never the reverse.
- `presets.csv` is generated from `combinations.json` by `gen_matrix.py`; edit
  the JSON, then regenerate the CSV.

## Adding or changing a tool

1. Put shared logic in `podgo.py`; keep task scripts thin.
2. Give the script a docstring with a `Usage:` line and a `main()` guard.
3. If it writes a file, note "generated by …" in that file and in
   [naming-and-registry.md](../presets/naming-and-registry.md)'s tool table.
4. Run [`validate_presets.py`](../../tools/validate_presets.py) — it must pass
   (0 errors) before and after.
