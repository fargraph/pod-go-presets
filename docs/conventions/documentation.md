# Documentation Conventions

How this `docs/` tree is organized and maintained. This is the **canonical map**:
if you add, move, split, or rename a doc, update this file too. It is enforced by
the `document` skill (invoke `/document`), but the rules apply to anyone editing
docs by hand.

↩ [conventions index](README.md)

## Audience & format

- **Audience:** a future developer working on this project.
- **Format:** GitHub-flavored Markdown only. Tables for matrices, fenced code
  blocks for JSON/shell/Python, `inline code` for keys, `@model` ids, filenames,
  and values.

## Layout

Docs are grouped into four **domain folders**, each carrying its own `README.md`
index:

```
docs/
├── README.md                     top-level index → links to every folder & doc
├── presets/                      how presets are structured, constrained & named
│   ├── README.md
│   ├── pgp-format.md             .pgp JSON shape, editing, serialization gotchas
│   ├── pgp-schema.md             formal JSON Schema (registry/pgp.schema.json) prose
│   ├── blocks-and-constraints.md block chain, free/built-in, ceilings, taxonomy
│   ├── business-rules.md         semantic rules (registry/rules.json) + verified/unverified
│   └── naming-and-registry.md    naming, name/file limits, registry, tools
├── knowledge/                    what hardware testing taught us
│   ├── README.md
│   ├── verified.md               hardware-verification ledger (confidence tiers)
│   ├── data-quality.md           real defects found in the library + fixes
│   ├── troubleshooting.md        on-device quirks & workarounds
│   └── lessons-learned.md        digest of non-obvious findings (links out)
├── reference/                    model catalog, id syntax, generated data, links
│   ├── README.md
│   ├── block-models.md
│   ├── model-id-conventions.md   @model string id anatomy
│   ├── usb-id-mapping.md         the separate usb_id system + why it's device-internal
│   ├── data-coverage.md          GENERATED by tools/coverage.py
│   └── resources.md              external links (Line 6 sources, community)
└── conventions/                  how to work on the project
    ├── README.md
    ├── code-conventions.md
    ├── project-conventions.md
    ├── best-practices.md
    └── documentation.md          (this file)
```

Keep new material in this shape: a topic file goes in the folder for its domain
and is linked from that folder's `README.md`, which is linked from the top index.
Add a new subfolder only when a genuinely new domain emerges, and give it a
`README.md` index when you do.

## The two invariants

1. **No orphans.** Every `docs/**/*.md` is reachable by following links from
   `docs/README.md`. Every doc is linked from its folder's `README.md`, and every
   folder `README.md` is linked from the top index.
2. **Two indexes in sync.** [`docs/README.md`](../README.md) is the full map; the
   `## Docs table of contents` in the working-root `CLAUDE.md` is a condensed
   "when you need X, read Y" pointer. A structural change updates both.

## Where content goes (routing)

| The new thing is… | Doc |
| --- | --- |
| `.pgp` JSON shape / a key / field / serialization | `presets/pgp-format.md` |
| A formal schema constraint (envelope, types, required fields) | `presets/pgp-schema.md` + `registry/pgp.schema.json` |
| Block-chain rules, free/built-in, ceilings, taxonomy, mandatory block | `presets/blocks-and-constraints.md` |
| A semantic/business rule + its status + demonstrator preset | `presets/business-rules.md` + `registry/rules.json` |
| Naming, name/file limits, registry contents, tool usage, add-a-preset | `presets/naming-and-registry.md` |
| A new `@model` id family / prefix / naming pattern | `reference/model-id-conventions.md` |
| Anything about the USB `usb_id` (wire encoding, the id↔`@model` map, decompiling POD Go Edit) | `reference/usb-id-mapping.md` |
| Authoritative model lists, category counts, Helix deltas | `reference/block-models.md` |
| An external link / source | `reference/resources.md` |
| A concrete library defect + fix | `knowledge/data-quality.md` |
| A confirmed / refuted hardware fact (verified/unverified status) | `knowledge/verified.md` + `registry/rules.json` |
| A preset that demonstrates a fact | `data-presets/demonstrations/manifest.json` |
| An on-device quirk or workaround | `knowledge/troubleshooting.md` |
| A convention / workflow / best practice | `conventions/` |
| A one-line "this surprised us" summary | `knowledge/lessons-learned.md` (links to the detail doc) |

**Edit in place** before creating a new file. Single source of truth: a fact that
touches two docs gets a **link**, not a copy.

## Sizing & splitting

- Keep files **focused and well under ~300 lines.** When a file exceeds that or
  starts covering two separable topics, split it and fix the indexes + back-links
  in the same change.

## Generated files

- [`reference/data-coverage.md`](../reference/data-coverage.md) is **generated by
  `tools/coverage.py`** — never hand-edit it. If it's stale, re-run the tool.
- `registry/presets.csv` is generated by `tools/gen_matrix.py` from
  `combinations.json`.

## File conventions

- Every file opens with an H1 title and a one-sentence purpose line. Every topic
  file adds a back-link to its folder index (`↩ [… index](README.md)`), and every
  folder index back-links to the top index (`↩ [Docs home](../README.md)`). The
  generated `reference/data-coverage.md` is exempt — its header is written by the
  tool.
- Folder `README.md` files are **indexes**: H1 + purpose + a list of the folder's
  files each with a one-line description + a back-link to `../README.md`.

## Folder READMEs outside `docs/`

Code/data folders (`registry/`, `tools/`, `data-presets/`, `presets/`) may carry a
short `README.md`: one paragraph on what the folder holds, then a **link** to the
authoritative doc under `docs/` — never a duplicate of it. This keeps GitHub's
folder view useful without creating a second source that drifts.

## Verified vs. unverified

Status is **binary**: ✅ **verified** (jointly confirmed with the owner **and** backed by a
demonstrator preset) vs ⬜ **unverified** (everything else — the honest default). Never
promote "imports cleanly" or a clean parse to verified. Record the status in
[`registry/rules.json`](../../registry/rules.json), reflect it in
[`verified.md`](../knowledge/verified.md) and [business-rules.md](../presets/business-rules.md),
and — where possible — wire the fact to a demonstrator in
[`data-presets/demonstrations/manifest.json`](../../data-presets/demonstrations/manifest.json).
Demonstrators are the known-good base preset plus one minimal edit where possible. See
[best-practices.md](best-practices.md).
